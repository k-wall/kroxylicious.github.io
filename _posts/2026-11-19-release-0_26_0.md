Kroxylicious 0.26.0 has hatched🐊!

0.26.0 picks up a critical OpenJDK security fix and resolves two high-severity vulnerabilities in the ACL authorizer. It also brings automatic downstream TLS certificate rotation, configurable post-quantum key exchange for both downstream and upstream TLS connections, client address visibility for filters, per-gateway PROXY protocol configuration, and container images for two new architectures. Take a look at [all the changes](https://github.com/kroxylicious/kroxylicious/blob/v0.26.0/CHANGELOG.md).

---

### Container Image: Critical OpenJDK Fix (RHSA-2026:100567)

Kroxylicious's container images install `java-21-openjdk-headless` from the UBI9 package repositories, so the 0.26.0 images incorporate Red Hat's [RHSA-2026:100567](https://access.redhat.com/errata/RHSA-2026:100567), published the day before this release. That advisory is rated **Critical** and fixes nine CVEs in OpenJDK 21, including CVE-2026-114938, a remote code execution vulnerability via memory corruption on x86-64 systems with AVX-512 VBMI.

If you run the official Kroxylicious container images, upgrading to 0.26.0 picks up the fix. If you build your own images or run the proxy outside of our containers, make sure your JDK is patched independently.

### Security Advisories

#### CVE-2026-118952: Principal Type Confusion and Incomplete Prefix Matching in the ACL Authorizer

**Affected:** Kroxylicious 0.18.0 through 0.25.1 when using the `kroxylicious-authorizer-acl` plugin with `like` (prefix) rules.

**Not affected:** If you do not use the ACL authorizer, or you only use exact-match rules, you are not affected.

**Description:** A `like` (prefix) rule written for one principal type (e.g. `Role`) could incorrectly match a principal of a different type that happens to share the same name prefix, and when rules had overlapping prefixes, a shorter, more restrictive rule could be silently skipped in favour of a longer one. In both cases, access could be granted that the rules file did not intend — with no indication that anything was wrong.

**Fix:** Prefix matching now checks principal/resource type correctly and evaluates every applicable prefix, not just one, so rules are enforced as written.

**Advisory:** [GHSA-qvv3-6w3q-hgqc](https://github.com/kroxylicious/kroxylicious/security/advisories/GHSA-qvv3-6w3q-hgqc)

#### CVE-2026-128424: Overly Permissive Regex Unescaping in the ACL Authorizer

**Affected:** Kroxylicious 0.18.0 through 0.25.1 when using the `kroxylicious-authorizer-acl` plugin with `matching /…/` regex rules containing backslash escapes.

**Not affected:** If you do not use the ACL authorizer, or your `matching` rules contain no backslash escapes, you are not affected.

**Description:** The code that unquotes `matching /…/` literals stripped the backslash from every `\X` escape sequence, not just `\/` and `\\`. This turned intentionally-literal regex metacharacters such as `\.`, `\d`, `\w`, `\s`, and `\b` into their broader regex meaning — for example, a rule meant to match only the literal topic `orders.v1` was silently enforced as a pattern where `.` matched any character — so rules could grant access more broadly than the operator intended, with no indication anything was wrong.

**Fix:** Unescaping is now restricted to the two sequences that should be literal, `\/` and `\\`; every other backslash escape passes through unchanged to the regex engine.

**Advisory:** [GHSA-x5xx-3j9w-x63g](https://github.com/kroxylicious/kroxylicious/security/advisories/GHSA-x5xx-3j9w-x63g)

If you run the ACL authorizer with `like` or `matching` rules, upgrade to 0.26.0 and review your rules files for any that may have been relying on the old, overly-permissive behaviour.

### Automatic Downstream TLS Certificate Rotation

A long-standing request ([#104](https://github.com/kroxylicious/kroxylicious/issues/104)) is finally delivered: virtual cluster gateways now detect when their downstream TLS certificate or key material changes on disk and reload it automatically, with no proxy restart and no dropped connections. This is particularly useful alongside cert-manager or other automated certificate issuance pipelines.

### Post-Quantum Key Exchange (PQC)

Following [Design Proposal 144](https://github.com/kroxylicious/design/blob/main/proposals/144-pqc-support.md), both downstream (client-facing) and upstream (cluster-facing) TLS gain new configuration to control post-quantum key exchange algorithms. Gateways and clusters can set a `namedGroups` attribute with `allowed` and `denied` lists — `allowed` also sets key exchange preference order — so you can opt in to PQC algorithms, or lock a connection down to only accept them. This isn't enabled automatically; it's an opt-in configuration you apply where you need it. Support for the PQC algorithms themselves comes from the JDK and varies by provider and version prior to Java 27.

### Client Address Visible to Filters

Implementing [Proposal 139](https://github.com/kroxylicious/design/blob/main/proposals/139-expose-client-address-to-filters.md), `FilterContext` now exposes `clientAddress()`, `peerAddress()`, and `clientProxyProtocolContext()` to filters, so filter authors can make decisions based on where a connection actually originated — including through a PROXY protocol-aware load balancer. The `ProtocolLogger` filter has also been updated to include both addresses in its output.

### Per-Gateway PROXY Protocol Configuration

**Breaking change:** PROXY protocol configuration has moved from the top-level proxy configuration to each `virtualClusters[].gateways[]` entry ([#5118](https://github.com/kroxylicious/kroxylicious/issues/5118), [#5263](https://github.com/kroxylicious/kroxylicious/pull/5263)). The `allowed` (auto-detect) mode has been removed, and `disabled` has been renamed `forbidden`, which is now the default. Move your `proxyProtocol` block inside each gateway that needs it, and rename `disabled` to `forbidden`.

### New Container Architectures

Proxy, operator, and admission webhook container images are now also published for `linux/ppc64le` and `linux/s390x` ([#4969](https://github.com/kroxylicious/kroxylicious/issues/4969)), in addition to the existing architectures. The proxy uses the NIO transport on these platforms.

### Other Changes to Note

- Maven 3.9.2+ is now required to build the project.
- Operator metrics have been migrated to the Java Operator SDK's `MicrometerMetricsV2` names and labels; dashboards and alerts using the previous `operator_sdk_` metrics will need updating.

See the [CHANGELOG](https://github.com/kroxylicious/kroxylicious/blob/v0.26.0/CHANGELOG.md#0260) for the complete list of changes, deprecations, and removals.
